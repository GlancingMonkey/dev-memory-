# 2026-11-16 Backend·RAG 개발·검증 기록

## 범위와 상태

11/18 마감을 위해 현재 사용자가 Backend와 RAG를 함께 구현한 작업 트리의 기록이다.
측정 기준은 develop `a6480d663264387f981ab136c85039ab6f4e904b`에 본 변경을 적용한 작업 트리다.
측정 당시 소스·샘플·설정은 해시와 보존본으로 남겼다. 게시·병합 상태는 이 문서가 포함된 PR에서 확인한다.
현재 기능 설명은 코드·실제 API 검사 기준이다. Windows 화면 조작과 팀 통합 완료를 의미하지 않는다.

- Backend: GET /filters, project·language 조건 검색과 적용 조건 응답.
- RAG: 같은 프로젝트·언어 안의 동일 코드 중복 제거, 전체 스니펫 예산 선택, 제외 사유·대표 ID 보존.
- Backend 연결: 한 요청의 동일 참고 자료·최종 메시지 계수 재사용, 기존 JSON/SSE·인용 검증 유지.
- 평가: 실제 코드 14개, 정답 질문 20개와 근거 부족 질문 5개. 기존 E5 세 모델 비교는 재실행하지 않았다.
- 문서와 .env.example을 실제 동작에 맞춰 갱신했다. 실제 .env와 API 키는 게시하지 않는다.

## Backend와 실제 DB

무필터·프로젝트·언어·두 조건·빈 조건·없는 조건·SQL 구문처럼 생긴 값·긴 조건·잘못된 limit을 실제 API에서 확인했다.
프로젝트와 언어 각각에 대해 **전역 Top-1에는 없던 코드가 조건 검색에서는 반환되는 사례**를 확인했다.
조건은 DB의 WHERE에서 적용한 뒤 거리 정렬·LIMIT을 수행한다.
프로젝트는 양끝 공백 제거 후 대소문자를 구분하고, 언어는 양끝 공백 제거·소문자 변환으로 비교한다.
응답 filters는 실제 적용한 정규화 조건이며 미지정 조건은 null이다.
목록 API는 같은 유효 벡터 기준으로 이름과 행 수를 반환한다. 같은 코드의 중복 행도 각각 센다.

평가 준비 전 8행에서, 원래 벡터가 없던 multiply의 기존 id=4를 ready로 재처리하고
실제 저장소 함수 9개를 기존 POST /snippets로 추가했다.
새 행은 이 환경의 id=9~17이며 다른 환경의 ID로 가정하지 않는다.
기존 원문·7개 필드·기존에 있던 벡터를 보존했다. id=4의 상태·벡터·updated_at 갱신은 의도한 변경이다.
입력 한도 실패였던 기존 행도 그대로 보존했다.

최종 DB는 17행, 유효 벡터 16개다.
모든 벡터는 768차원이며 norm은 약 1이다.
이후 모든 읽기·모델 평가·스트리밍 확인 전후에 DB 전체 스냅샷이 동일했다.
Git으로 다른 PC의 DB·실제 원본 파일까지 공유되는 것은 아니다.

## E5 검색 품질

실제 저장소 함수 9개와 기존 개발 스니펫 5개를 사용했다.
동일 코드의 중복 행을 포함해 검색 가능한 행은 16개이며, 기대 코드의 동등한 DB 행은 함께 정답으로 인정했다.

## 작은 예산에서의 코드 누락과 품질

운영 기본값 4000은 유지했다. 별도 512토큰 경계 검사에서 실제 계수 494토큰에 전체 코드 4개가 들어갔다.
원문을 중간에서 자르지 않았고 제외 ID·이유를 기록했다.
이 경계 검사의 전체 입력 계수는 997이며 제공자 usage나 생성 결과가 아니다.

수정 지시문에서 q01과 q16을 512토큰으로 각 방식 1회씩 추가 생성했다.
q01은 기대 코드가 남아 양쪽 모두 정상 설명했다.
q16은 9위의 필요한 코드가 예산에서 빠져 양쪽 모두 근거 부족을 반환했다.
4000 예산에서 답할 수 있었던 질문이 작은 예산에서는 답하지 못한 사례다.
토큰을 줄이는 것만으로 품질을 보장할 수 없고, 예산·검색 순위를 함께 평가해야 한다.

## 실행과 18일 확인

[평가 실행 가이드](../rag/experiments/deadline_eval/README.md)의 기본값은 읽기 전용 검색이다.
--apply는 자료 추가·기존 미처리 행 재처리를, --ask는 실제 모델 생성을 명시적으로 켠다.
중단된 요청을 자동 재전송하지 않고 조건이 바뀐 결과를 덮어쓰지 않는다.

이번에 직접 확인하지 않은 항목은 다음과 같다.

- develop 최종 통합과 실제 팀 환경의 완료 여부는 PR·이슈의 확인 기록을 따른다.
- 팀원이 새로 받은 환경의 실제 DB/원본 파일 재현.
- PR #51의 Windows 개발 호스트에서 실제 범위 선택·해제·빈 결과·오류·취소·늦은 응답.
- 답변 본문 [S1] 직접 클릭, 원본 이동·복사·빈 편집기 삽입·후속 질문·테마.
- 외부 첫 사용자 시험, 독립 답변 평가, 포스터 제출·학술제 평가.
- 다른 프로젝트의 동일 코드는 유지한다. 동일 프로젝트의 다른 파일은 대표 출처만 선택하므로 파일 위치 자체가 중요한 질문은 추가 검토가 필요하다.
- 새 모델·긴 코드 자동 분할·새 관련성 임계값·Marketplace 배포는 이번 범위에 추가하지 않았다.
