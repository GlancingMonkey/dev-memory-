## Extension · @applecider2

Backend가 준비한 요청·응답:

- GET /filters → projects·languages 각각 [{name, count}]. count는 유효 벡터가 있는 행 수이며 중복 저장 행도 각각 센다.
- GET /search → q·limit, 선택 project·language.
- 미지정·공백 조건은 제한 없음. project는 대소문자를 구분하고 language는 소문자로 맞춘다. 두 조건은 AND다.
- 정규화한 조건은 최대 200자이며 조건은 DB 전체 후보에 적용한 뒤 Top-K를 고른다.
- 검색 응답 filters에는 실제 적용한 project·language를 반환한다. 미지정은 null이다.
- POST /ask는 전체 DB를 검색한다. 이번 검색 범위를 보내지 않으며 화면의 범위 무시 안내를 유지한다.
- 저장·일반 검색·필터 목록에서 LLM을 호출하지 않는다.

실제 화면 확인:

- [ ] mock=false와 올바른 Backend 주소, health를 확인한다.
- [ ] 프로젝트만·언어만·둘 다·전체 해제·없는 조건에서 API와 같은 결과인지 확인한다.
- [ ] 전역 Top-1에 없는 프로젝트·언어의 코드도 조건 검색으로 나오는지 확인한다.
- [ ] 조건 변경 후 늦은 응답이 새 결과를 덮지 않는지, 오류·시간 초과·취소 뒤 복구되는지 확인한다.
- [ ] AI 답변의 [S1]을 직접 눌러 해당 참고 코드로 이동·펼침을 확인한다.
- [ ] 원본 열기·줄 범위·복사·새 빈 편집기 삽입·후속 질문·테마를 확인한다.

PR #51 e9f50b7에서 단위 검사 51개·TypeScript·ESLint·빌드와 실제 API 응답 parser 대조는 통과했다.

**과거 스니펫과 현재 파일 위치:** 실험 샘플은 측정 당시 코드·줄 번호를 보존한다.

평가 자료 준비는 [평가 안내](../rag/experiments/deadline_eval/README.md)를 따른다.
Dev Container Bash의 최신 코드 루트에서 먼저 다음을 실행한다.

```bash
uv run --locked python -m rag.experiments.deadline_eval.seed --output out/reports/2026-11-18-preflight.json
```

기본은 읽기 전용이다. 출력에서 대상 자료와 기존 행을 확인한 뒤 필요할 때만 실행한다.

```bash

```

--apply는 없는 샘플을 기존 저장 API로 추가하고, 일치하는 미처리 행은 같은 ID로 처리한다.
이미 있는 벡터는 덮어쓰지 않고, 해결되지 않은 입력 오류도 그대로 재시도하지 않는다.
같은 출력 파일이 있으면 덮어쓰지 않는다. 이전 기록을 지우지 말고 새 결과 이름을 사용한다.
이 자료는 **역사적 검색·RAG 평가 입력**이다. 실제 원본 이동용 현재 파일은 Extension 담당과 별도로 저장·대조한다.
실제 모델 답변 재평가는 --ask로 명시한 경우에만 수행하며 인수인계만을 위해 기존 유료 실험을 반복하지 않는다.

## Backend · @wanghaiwen05-ui

이번에는 RAG 담당자가 구현을 함께 지원했다.
수정 위치:

| 파일 | 역할 |
|---|---|
| backend/routers/filters.py · schemas/filters.py | 목록 API와 응답 타입 |
| backend/routers/search.py · schemas/search.py | 입력 정규화·검증·적용 조건 응답 |
| backend/database.py | 안전한 조건 SQL·Top-K 이전 필터·목록 집계 |
| backend/routers/ask.py | 요청 안 실제 계수 재사용·기존 JSON/SSE 연결 |
| rag/context.py | 원문을 보존하는 중복 제거·예산 선택·출처 ID·제외 이유 |

Dev Container Bash의 저장소 루트에서 실행한다.

```bash
uv sync --locked
uv run --locked python -m unittest discover -s tests -p 'test_*.py' -v
uv run --locked uvicorn backend.main:app --host 0.0.0.0 --port 8000
```

uv sync는 잠긴 의존성을 준비하고, unittest는 자동 검사를 실행하며, uvicorn은 서버를 시작한다.
자동 검사 80개 통과 기록이 있으며 DB·모델 연결과 실제 화면은 별도로 확인한다.
DB가 필요한 경로는 기존 DATABASE_URL을 사용한다.
POST /ask의 실제 계수·생성에는 OPENAI_API_KEY가 필요하다. 키는 무시된 .env에만 둔다.

다른 터미널 또는 같은 PC 브라우저에서 확인한다.

```bash
curl http://127.0.0.1:8000/health
curl http://127.0.0.1:8000/filters
curl -G http://127.0.0.1:8000/search --data-urlencode 'q=짝수만 고르는 코드' --data-urlencode 'language=python' --data-urlencode 'limit=3'
```

정상: health=ok, filters의 이름·count가 DB와 일치하고 search의 filters.language=python이다.
입력 검증 오류는 422, DB·모델·키 준비 문제는 경로별 계약의 503으로 확인한다.
root /의 404는 health 실패를 뜻하지 않는다.
서버 로그와 DB를 확인하기 전에 저장 POST를 반복하지 않는다.
