# 후속 개발 계획

2026-11-05 기준으로 **저장 → 자동 임베딩 → 검색 API → Extension 결과·원본 이동**까지 통합을 확인했습니다. 근거는 [통합 검증 기록](INTEGRATION_TEST_2026-11-05.md)입니다.

아래는 다음 작업을 정할 때 사용할 제안 순서입니다. 일정·새 API·모델·수치를 확정한 계약이 아닙니다. 팀이 범위를 합의한 뒤 작은 기능 하나씩 구현하고 검증합니다.

## 1. 실제 코드로 검색 품질 확인

| 항목 | 내용 |
|---|---|
| 주 담당 | RAG, 팀원은 자신의 코드·질문 제공 |
| 입력 | 실제 프로젝트 코드와 자연어 질문 20~30개, 질문별 기대 코드 |
| 할 일 | 현재 E5의 순위·실패 사례 기록, 유사한 코드·중복 저장·관련 없는 질문 확인 |
| 완료 기준 | 평가 샘플·기준 커밋·환경·Hit@K·질문 응답 시간·실패 사례를 재현 가능한 기록으로 보관 |

기존 세 모델 비교는 그대로 보존합니다. 먼저 현재 E5가 어떤 질문에서 부족한지 확인하고, 그 질문을 해결하는 데 필요할 때 비교 모델을 추가합니다. 측정 전 목표치를 달성한 것처럼 쓰지 않습니다.

## 2. 검색의 범위와 긴 코드 처리 합의

- **Backend·Database·Extension:** 프로젝트·언어 조건을 DB 검색 단계에 적용하는 요청·응답 규칙을 합의합니다. 현재 UI 필터는 이미 받은 Top-K 안에서만 동작합니다.
- **RAG·Backend·Database:** 512토큰을 넘는 코드의 분할 단위, 원문과 조각의 관계, 줄 번호·벡터·재처리 방식을 설계합니다. 현재 동작은 원문 보존 후 embedding_input_invalid이며 자동 분할은 없습니다.
- **공동 확인:** 조건을 만족하는 코드가 검색 후보에 포함되는지, 원본 이동이 맞는지, 기존 저장·실패 보존이 유지되는지 검증합니다.

범위가 커지면 두 작업을 별도 PR로 나눕니다. 관련성 기준점과 중복 제거도 실제 실패 사례를 근거로 정합니다.

## 3. 선택적으로 Ask AI 연결

| 영역 | 맡을 일 |
|---|---|
| RAG | 검색 결과에서 참고 코드 선택, 출처가 포함된 Context 구성 |
| Backend | 팀이 확정한 Ask AI 계약, LLM 연결·오류 처리 |
| Extension | 일반 검색과 Ask AI를 구분한 실행·대기·답변·출처 표시 |
| Database | 추가 저장 항목이 필요한지 검토하고 필요한 변경만 적용 |

완료 기준은 **일반 검색에서는 LLM을 호출하지 않고**, 사용자가 Ask AI를 요청했을 때만 관련 코드를 근거로 답변하는 것입니다. 관련 코드 부족·LLM 오류도 확인합니다. LLM 제공자·모델·API 이름은 구현 전에 합의하며 비밀값을 저장소에 올리지 않습니다.

## 4. Context Token Budget 최적화

관련성이 낮은 후보와 중복을 줄이고, 토큰 수를 계산해 정한 예산 안에서 참고 코드를 선택합니다. 예산과 토큰 계산 방식은 채택할 LLM에 맞춰 정합니다.

같은 질문 묶음으로 최적화 전후의 **Context 토큰 수·답변 품질·응답 시간**을 비교합니다. 토큰 절감률만으로 품질 향상을 주장하지 않고 제외된 코드가 답변에 미친 영향도 기록합니다.

## 5. 최종 통합과 발표

환경 재현, 정상·실패 경로, 실제 코드 검색 품질, 시연 순서를 점검합니다. 변경 사항을 develop에서 통합 검증한 뒤 발표·안정 버전의 main 반영을 별도로 진행합니다.
