## 저장 결과 안내

별도 작업 영역과 로컬 시험 서버(18002)로 계약 형태의 응답을 보냈다. 실제 DB INSERT나 임베딩 생성 시험이 아니다.

| 시험 응답 | 실제 확인한 화면 |
|---|---|
| HTTP 200, ID 900001, ready | 검색 준비됨 |
| HTTP 200, ID 900002, failed | 원문 저장 안내와 검색 준비 실패 |
| HTTP 503, ID 900003, 상태 null | ID 유지, 검색 준비 확인 필요, 같은 요청 재전송 주의 |
| HTTP 503, detail만 있고 ID 없음 | 저장 여부 확인 필요, 성공 ID를 새로 표시하지 않음 |

각 조건의 POST는 한 번씩이었다. 자동 재전송은 없었다. 900001~900003은 시험 응답의 숫자이며 실제 DB 행이 아니다. 시험 저장 기록은 별도 작업 영역에 남기고 실제 작업 영역 기록과 구분했다.

이 결과와 [11/21 필터·검색 복구·복사 검증](INTEGRATION_TEST_2026-11-21.md), PR #59 병합 확인을 근거로 #40을 완료 처리했다.

## 개인 키와 서버 기본 키

- 서버 기본 키 선택 시 ‘내 키 저장됨’으로 표시되고, 시험 요청에 개인 키 헤더가 없었다.
- 내 키 선택 시 시험 요청에 개인 키 헤더가 있었다. 로그에는 헤더 유무만 기록했다.
- 모의 HTTP 401·403은 모두 ‘키 확인 필요’로 표시되고 키 설정·서버 기본 키 재시도 버튼을 제공했다.
- 사용자가 ‘서버 기본 키로 다시 묻기’를 누른 뒤에만 추가 요청이 한 번 발생했고, 해당 요청에는 개인 키가 없었다.
- 사용자가 다시 등록할 키를 준비한 뒤 삭제했다. 창을 다시 로드해도 ‘내 키 없음’이 유지됐다.
- 사용자 PC에서 개인 키를 재등록한 뒤 창을 다시 로드해 ‘내 키 사용 중’을 확인했다. 키 값을 채팅·Git·시험 로그로 받지 않았다.

이 시험은 선택·전송·저장/삭제·오류 안내 확인이다. 실제 제공자의 인증·권한 오류나 키의 유효성을 새로 측정하지 않았다. 기존 세 제공자의 실제 연결 기록과 구분한다.

## 원본 변경·비교·키보드와 어두운 테마

실제 프로젝트 파일 대신 새로 만든 `ui-save-fixture/sample.py`와 합성 검색 결과 ID 990001을 사용했다.

- 최초 두 줄과 저장 코드가 같을 때 ‘원본 같음’을 확인했다.
- 임시 파일의 `value > 0`을 `value >= 0`으로 바꾸자 ‘원본 바뀜’이 표시됐다. ‘바뀐 부분 보기’는 왼쪽 저장 코드 `>`, 오른쪽 현재 파일 `>=`를 보여줬다.
- 현재 파일의 두 줄을 선택하고 ‘비교’를 누르면 왼쪽 선택 코드 `>=`, 오른쪽 저장 코드 `>`로 표시됐다.
- 함수 위에 두 줄을 추가하자 ‘위치 이동’과 3~4줄의 실제 원본 열기를 확인했다.
- 임시 파일의 이름을 잠시 바꿨을 때 ‘원본 위치 연결’ 안내가 나왔다. 파일이 없어도 저장된 두 줄을 복사해 사용할 수 있었다.
- 임시 파일을 원래 이름·내용으로 복구했다. `Ctrl+Alt+F → Esc → ↓ → Enter`로 마우스 없이 1~2줄 원본 열기를 확인했다.
- 시험 작업 영역에만 어두운 테마를 적용해 코드와 상태 표시를 읽을 수 있음을 사용자가 확인했다. 시험 뒤 테마 설정을 제거했다. 전체 접근성 기준의 정식 평가를 뜻하지 않는다.

|---|---:|---|
