# Code Memory Extension

VS Code에서 선택한 코드·메타데이터를 저장하고, Backend의 실제 검색 결과를 표시하는 TypeScript Extension이다.

## 현재 기능

| 흐름 | 제공 기능 |
|---|---|
| 저장 | 코드 선택·함수 범위 인식, 메타데이터 수집, 중복 실행 방지, 원문 저장·검색 준비 상태 구분 |
| 검색 | 자연어 검색, 순위·ID·유사도·코드 위치, 최근 검색·결과 복원, 간단히 보기·결과 필터 |
| 코드 활용 | 원본 열기, 복사·들여쓰기 맞춤 삽입, 선택 코드와 비교, 비슷한 코드 찾기 |
| 사용 안내 | 실제 서버·mock 표시, 연결 확인, 저장 기록, 제한 시간 설정, 시작하기 안내 |

함수 범위·이름은 언어 확장이 제공하는 코드 구조를 우선 사용하며 상황에 따라 직접 선택·수정이 필요하다. 아래 사용법에서 조건과 설정을 확인한다.

저장·검색 요청과 응답은 [API_CONTRACT.md](../API_CONTRACT.md)를 따른다. Backend는 원문을 먼저 커밋한 뒤 자동 Embedding과 벡터·상태 저장까지 기다려 응답한다. 저장과 검색은 LLM을 호출하지 않는다. RAG/LLM 답변은 후속 작업이다.

## 실행 전 준비

이 가이드는 **같은 PC에서 Backend는 Dev Container, Extension은 Windows 로컬**로 실행한 검증 방법이다.

- Backend의 /health와 /docs에 Windows 브라우저로 접속할 수 있어야 한다.
- 실제 DB에 embedding vector(768), embedding_status, embedding_error가 필요하다. [개발 가이드](../docs/DEVELOPMENT.md)에서 스키마와 Backend의 E5 warmup을 확인한다. 새 저장 응답이 ready이면 검색할 수 있고, 기존 미처리·실패 행은 [재처리 CLI](../rag/README.md)로 확인한다.
- Windows에도 Node.js·npm이 필요하다. Dev Container의 Node 설치와 Windows 설치는 별개다.
- package.json의 VS Code 요구 범위는 `^1.138.0`이다. [2026-11-05 검증](../docs/INTEGRATION_TEST_2026-11-05.md)에서는 VS Code 1.145.0 x64, Node v24.20.0, npm 11.19.0을 사용했다.

## 빌드

아래 경로는 검증 때 사용한 예시다. 본인의 저장소 경로로 바꾼다. Windows PowerShell에서 실행한다.

```powershell
cd C:\dev\capstone-rag\extension
npm.cmd ci
npm.cmd run compile
```

compile은 TypeScript 검사 → ESLint → esbuild 번들링 순서다. 각 단계가 성공한 뒤 다음 작업을 진행한다.

## 개발 호스트 열기

테스트할 프로젝트 폴더를 먼저 준비한다. `C:\dev\mvp-save-test`는 별도 로컬 테스트 폴더 예시이며 저장소에 포함된 폴더가 아니다.

빌드가 끝난 뒤 Windows PowerShell에서 실행한다.

```powershell
code.cmd --new-window --extensionDevelopmentPath="C:\dev\capstone-rag\extension" "C:\dev\mvp-save-test"
```

새로 열린 **확장 개발 호스트**에서 테스트한다. 같은 Extension을 다시 빌드했다면 개발 호스트를 다시 로드하여 변경을 반영한다.

F5의 Run Extension을 사용하는 경우에는 이 extension 폴더 자체를 VS Code에서 열고 [.vscode/extensions.json](.vscode/extensions.json)의 권장 확장을 확인한다. watch 작업의 `$esbuild-watch`는 권장 esbuild problem matcher 확장을 사용한다. 위 명령어 실행 방식은 사전 빌드한 dist를 사용한다.

## 실제 API 설정

새로 열린 **확장 개발 호스트**에서 Ctrl+,를 누르고 **Workspace / 작업 영역** 탭에서 codeMemory를 검색한다. Backend를 연 Dev Container 창의 설정과 구분한다. 설정 변경 후 개발 호스트 하단 상태 표시줄의 실제 모드·주소가 원하는 값인지 확인한다.

| 설정 | 기본값 | 실제 연동 테스트 값 |
|---|---|---|
| codeMemory.mock | true | false |
| codeMemory.apiUrl | http://localhost:8000 | http://127.0.0.1:8000 또는 실제 전달 주소 |
| codeMemory.searchLimit | 10 | 검색 결과 최대 개수 (API 계약 범위 1~20) |
| codeMemory.confirmFunctionName | false | true면 저장 전에 함수 이름 입력창이 뜬다 |
| codeMemory.saveTimeoutSeconds | 10 | 저장 요청 제한 시간(초). 실제 측정 후 팀이 정한다 |
| codeMemory.searchTimeoutSeconds | 10 | 검색 요청 제한 시간(초) |

Mock이 true이면 서버를 호출하지 않는다. 검색은 질문과 관계없이 고정 샘플 3개를 표시하고 저장은 가짜 id를 반환한다. 실제 검증에서는 false로 설정한다.

현재 모드는 VS Code 아래 상태 표시줄에 항상 보인다.

| 표시 | 뜻 |
|---|---|
| `Code Memory: mock` (노란 배경) | mock. 서버를 호출하지 않음 |
| `✓ Code Memory: 127.0.0.1:8000` | 실제 서버. `GET /health` 응답 정상 |
| `✕ Code Memory: 127.0.0.1:8000 연결 안 됨` (빨간 배경) | 실제 서버. `/health` 확인 실패 — 서버 실행·주소·포트 전달 확인 |

실제 서버 모드에서는 30초마다, 그리고 설정이 바뀔 때 `/health`를 다시 확인한다. `/health` 정상은 서버가 켜져 있다는 뜻이며 DB 저장 성공까지 뜻하지는 않는다.

상태 표시줄을 누르면(또는 명령 팔레트의 **Code Memory: 모드 바꾸기**) mock / 실제 서버 전환, 서버 주소 바꾸기, 연결 다시 확인, 설정 열기를 고를 수 있다. mock일 때는 검색 패널 위에도 노란 MOCK 안내가 뜬다.

## 저장

1. 개발 호스트에서 프로젝트 폴더를 연다.
2. 파일을 프로젝트 안에 저장하고 코드 범위를 선택한다. 선택이 없으면 언어 확장의 코드 구조에서 커서를 감싼 함수를 찾아 전체 범위를 선택한다. 함수 범위를 인식하지 못하면 직접 코드를 선택한다.
3. 명령 팔레트의 **Code Memory: 코드 저장**, 우클릭 메뉴 또는 Ctrl+Alt+S를 실행한다.
4. 오른쪽 아래에 `Code Memory: 저장 중…`이 뜬다. 응답이 올 때까지 저장 명령을 다시 실행해도 요청을 보내지 않는다.
5. 출력 → Code Memory에서 POST 주소·HTTP 상태·실제 반환 id를 확인한다.
6. DB에서 그 id를 조회해 코드 원문을 포함한 7개 저장 필드를 대조한다.
7. ready 응답의 **검색에서 확인**을 누르면 검색 패널이 열리고 함수 이름(없으면 파일 이름)으로 바로 검색한다. failed 또는 상태 확인 불가 응답은 경고와 저장된 ID를 안내한다. 검색 패널이 열려 있으면 패널 아래에도 결과 알림이 잠깐 뜬다.

### 함수 이름

함수 이름은 VS Code가 알고 있는 코드 구조(개요 창에 나오는 기호)에서 선택 시작 줄을 감싸는 가장 안쪽 함수 이름을 쓴다. 함수가 없으면 클래스 이름, 둘 다 없으면 `null`이다. 그 언어의 코드 구조를 못 받으면(언어 확장 없음 등) 예전 정규식 방식(python·typescript·javascript·java)으로 찾는다.

### 검색 준비 상태

확정된 필드는 id, message, embedding_status, embedding_error다. message는 원문 저장 완료 시 `snippet saved`다. 과거 별칭 필드는 공식 필드를 대신하지 않는다.

| HTTP / 상태 | 알림 | 저장 기록 |
|---|---|---|
| 200 / ready | 저장 완료 · 검색 준비 완료 | ID 유지 · 검색 준비됨 |
| 200 / failed | 원문 저장 완료 · 검색 준비 실패 | ID 유지 · 검색 준비 실패 |
| 503 / 저장된 ID + null | 원문 저장 완료 · 검색 준비 상태 확인 불가 | ID 유지 · 검색 준비 확인 필요 |
| 503 / detail만 있음, 시간 초과, 응답 확인 불가 | 저장 여부 확인 필요 · 재전송 전 서버 로그·DB 확인 | 저장 여부 확인 필요 |
| 422 | 요청 필드·입력값 검증 오류 | 실패 |

HTTP 503에 id와 message가 있고 embedding_status=null, embedding_error=embedding_storage_failed이면 원문은 저장된 상태다. ID를 보존하고 해당 행부터 확인한다. null은 API가 최종 상태를 확인하지 못했다는 뜻이며 DB의 새 상태 값이 아니다.

DB의 pending은 임베딩 미처리 상태다. 과거 저장 기록에 pending이 있으면 `임베딩 미처리`로 표시하며 백그라운드 처리 중이라고 안내하지 않는다. 현재 POST의 정상 완료 응답 상태는 ready 또는 failed다.

입력 한도 초과의 failed/embedding_input_invalid는 같은 입력을 그대로 재처리하지 않는다. 생성·저장 실패는 기존 ID의 원문과 상태를 확인한 뒤 재처리 CLI를 사용한다. 같은 POST를 자동 재전송하지 않는다.

### 저장 전 확인

`codeMemory.confirmFunctionName`을 켜면 저장 직전에 자동으로 찾은 함수 이름이 입력창에 뜬다. 고치거나 그대로 Enter, 비우면 이름 없이(`null`) 저장, Esc는 저장 취소다. 정규식 추출이 틀렸을 때 쓴다.

저장할 때마다 검색 패널 아래 **저장 기록**에 한 줄씩 남는다 (최대 20개, 폴더별). 원문 저장이 확인된 경우 실제 ID와 검색 준비 상태를 유지한다. mock, 요청 실패, 저장 여부 확인 필요도 구분한다. 기록을 누르면 함수 이름으로 검색하며 실패·확인 불가 상태만으로 검색 가능하다고 판단하지 않는다.

저장 요청은 `codeMemory.saveTimeoutSeconds`(기본 10초) 안에 응답이 없으면 `응답 시간 초과`로 안내한다. 출력 패널의 POST 줄 끝과 저장 기록에 실제로 걸린 시간이 남으니, 제한 시간을 정할 때 이 값을 쓴다. 이때 서버에는 저장됐을 수 있으므로 다시 저장하지 말고 서버 로그·DB를 먼저 확인한다. 시간 초과 뒤 자동으로 다시 보내지 않는다.

아직 디스크에 저장하지 않은 새 파일(Untitled), 프로젝트 밖 파일, 함수 범위도 자동 인식할 수 없는 빈 선택, 공백뿐인 코드는 안내 후 저장을 중단한다. 원본 절대 경로는 Extension 내부에서 사용하고 요청에는 기존 7개 필드만 넣는다.

## 검색과 코드 사용

왼쪽 Code Memory 검색창에 자연어를 입력한다. 실제 요청은 GET /search?q=...&limit=10이고 결과는 Backend 순서대로 표시한다.

- 카드는 `순위 · 함수 이름 · 유사도`, `파일 : 시작–끝 줄`, `프로젝트 · 언어 · id` 순서로 보인다. 순위와 id는 Swagger 결과와 대조할 때 쓴다.
- 유사도는 score(코사인 유사도, -1~1)를 소수점으로 표시한다. 클수록 유사하며 정답 확률이나 정확도 퍼센트가 아니다.
- 코드는 실제 줄 번호(start_line부터)와 함께 보이고, 6줄이 넘으면 접힌다. **N줄 전체 보기**로 펼친다.
- **원본 열기** 또는 파일 이름 링크: 이름이 같은 프로젝트 폴더가 열려 있고 상대 경로의 실제 파일이 있어야 한다. 결과를 받을 때 미리 확인해서, 열 수 없으면 링크 대신 **원본 없음** 표시와 함께 버튼이 비활성화된다. 표시에 마우스를 올리면 이유가 나온다.
- **삽입**: 현재 편집기의 선택 영역을 결과 코드로 바꾼다. 결과 코드의 공통 들여쓰기를 걷어내고 커서 위치의 들여쓰기에 맞춰 넣는다. 검증할 때는 새 빈 편집기를 사용한다.
- **비교**: 왼쪽에 지금 에디터에서 선택한 코드(선택이 없으면 마지막으로 **비슷한 코드 찾기**에 쓴 코드), 오른쪽에 저장된 코드를 VS Code 비교 화면으로 연다. 읽기 전용이라 닫을 때 저장을 묻지 않는다.
- 코드에는 문법 색이 칠해진다 (문자열·주석·숫자·키워드·함수·타입·데코레이터). 여러 줄 주석·문자열도 이어서 칠한다. 에디터만큼 정확하지는 않다.
- **복사**: 결과 코드 원문을 클립보드에 복사한다. 버튼이 잠깐 `복사됨 ✓`으로 바뀐다.
- 검색 응답을 기다리는 동안 검색 버튼이 잠긴다.
- 검색창을 누르면 최근 검색어 5개가 펼쳐진다. ↑↓로 고르고 Enter, Esc로 닫는다. **지우기**로 비운다.
- 마지막 검색어와 결과는 폴더(워크스페이스)별로 저장돼, 다시 열면 `지난 검색`으로 복원된다.
- **Ctrl+Alt+F** 또는 명령 팔레트의 **Code Memory: 검색창 열기**로 검색 패널을 열고 검색창에 커서를 둔다.
- 검색창과 요약줄은 스크롤해도 위에 고정된다.
- 요약줄의 **자세히 / 간단히**: 간단히는 결과를 한 줄씩(순위·이름·위치·유사도) 보여준다. 줄을 누르면 원본 열기. 선택은 기억된다.
- 결과의 언어나 프로젝트가 2가지 이상이면 요약줄 아래에 필터가 나온다. **서버가 반환한 최대 limit개 안에서만** 화면 결과를 거르며, DB 전체를 조건 검색하는 기능은 아니다. 걸러도 순위 숫자는 서버 순위 그대로다.
- 요약줄의 **기록 복사**: 질문·모드(mock/실제 서버 주소)·시각과 결과(순위·id·함수·위치·유사도)를 마크다운 표로 복사한다. 필터 중이면 보이는 결과만 복사한다.
- 요약줄의 **×**: 결과를 지우고 처음 화면(예시 질문)으로 돌아간다. 지난 검색 복원도 지워진다.
- 결과가 없으면 **다른 말로 검색** / **모드 바꾸기** 버튼, 오류가 나면 **다시 시도** 버튼이 나온다. 시간 초과는 노란색, 연결·서버 오류는 빨간색이다.
- 결과 카드의 언어 앞 색 점은 언어별 색이다 (python 파랑, typescript 하늘색 등).
- 키보드: 검색창에서 ↓ 로 결과 카드로 이동한다. 카드에서 ↑↓ 이동, Enter 원본 열기, C 복사, I 삽입, D 비교, Esc 검색창.
- **비슷한 코드 찾기**: 에디터에서 코드를 선택하고 우클릭 → **Code Memory: 비슷한 코드 찾기**. 선택한 코드를 그대로 질문으로 보내 기존 `GET /search`로 검색한다 (줄바꿈은 공백으로, 1000자까지). 코드를 질문 자리에 넣는 방식이라 자연어 질문보다 결과 품질이 낮을 수 있다.

DB에 코드와 경로가 저장되어도 PC에 원본 파일이 자동으로 생성되지는 않는다.

## 시작하기 안내

명령 팔레트의 **Code Memory: 시작하기 안내** 또는 검색 패널 처음 화면의 **처음이면 시작하기 안내 보기**를 누르면 VS Code 시작 화면에 4단계 안내(모드 확인 → 저장 → 검색 → 찾은 코드 쓰기)가 열린다. 각 단계의 버튼을 누르면 완료 표시가 된다.

## 단위 테스트

VS Code 없이 도는 로직(`src/logic.ts`: 정규식 함수 이름 찾기, 함수 고르기, 줄 번호 보정, 들여쓰기 맞추기, 저장 응답 읽기)을 테스트한다.

```powershell
cd C:\dev\capstone-rag\extension
npm.cmd run test:unit
```

`out/` 폴더에 컴파일 결과가 생긴다. 커밋하지 않는다. 저장 응답 검사는 ready·failed, 저장된 ID가 있는 503과 없는 503, 계약에 맞지 않는 응답을 포함한다. [2026-11-05 검증](../docs/INTEGRATION_TEST_2026-11-05.md)에서는 26개 테스트가 통과했다.

## .vsix 패키지 만들기

```powershell
cd C:\dev\capstone-rag\extension
npm.cmd run vsix
```

검사·린트·배포용 빌드 뒤 `code-memory-0.0.1.vsix`가 생긴다. VS Code의 확장 화면 `…` → **VSIX에서 설치**로 설치한다. `publisher`는 `dev-memory-team`(임시)이다. 마켓플레이스에 올리지 않으면 바꿀 필요 없다. `.vsix` 파일은 커밋하지 않는다.

## 오류 확인

| 증상 | 확인할 내용 |
|---|---|
| tsc를 찾을 수 없음 | extension 폴더에서 npm.cmd ci 성공 여부 |
| npm.ps1 실행 정책 오류 | Windows에서는 npm.cmd 사용; 작업 자동화 프로필은 저장소 설정의 cmd.exe 확인 |
| npm ci가 esbuild.exe의 EPERM으로 실패 | 실행 중인 watch·디버그 작업을 먼저 종료한 뒤 재시도 |
| 잘못된 problemMatcher: $esbuild-watch | 권장 esbuild problem matcher 확장 확인 또는 사전 빌드 후 위 명령으로 개발 호스트 실행 |
| 서버 연결 실패 | Backend 실행, apiUrl, Dev Container 8000 포트 전달 확인 |
| 저장 응답 시간 초과 / 저장 여부 확인 필요 | 같은 POST를 반복하지 말고 서버 로그와 DB에서 저장 여부부터 확인 |
| 503 응답에 저장된 ID가 있음 | 원문은 저장됨. 해당 ID의 DB 상태 확인 후 기존 행 재처리 |
| embedding_input_invalid | 원문은 보존됨. 입력 한도와 코드를 확인하고 같은 입력의 반복 재처리 중단 |
| 검색 응답 시간 초과 | 첫 검색은 모델 준비로 오래 걸릴 수 있음. 잠시 후 다시 검색 |
| 첫 검색이 오래 걸림 | Swagger에서 모델 준비와 첫 검색이 끝난 뒤 UI 검색 |
| 결과가 없음 | DB의 검색 가능한 embedding 행이 준비됐는지 확인 |
| 원본 파일을 찾을 수 없음 / 원본 없음 표시 | 현재 열린 프로젝트 이름과 상대 경로의 실제 파일 존재 확인 |
| 상태 표시줄이 계속 mock | 설정의 codeMemory.mock 체크 해제 여부 확인 |
| Ctrl+Alt+F가 동작하지 않음 | 다른 프로그램·확장이 같은 단축키를 쓰는지 확인. 명령 팔레트의 Code Memory: 검색창 열기로 대신 실행 |

전체 실행 순서와 자동 Embedding은 [개발 가이드](../docs/DEVELOPMENT.md), 기존 ID 재처리는 [RAG 가이드](../rag/README.md)를 따른다. 실제 확인한 결과는 [2026-11-05 검증 기록](../docs/INTEGRATION_TEST_2026-11-05.md), 이전 수동 벡터 준비 단계의 기록은 [2026-10-28 검증](../docs/INTEGRATION_TEST_2026-10-28.md)에 보존한다.

과거 `scripts/mock_server.py`는 HTTP 201/id만 반환하는 초기 저장 시험 도구다. 현재 API 계약 검증에는 실제 Backend를 사용한다. Extension 설정 mock=true는 이 스크립트를 호출하지 않는 별도의 UI 모의 모드다.
